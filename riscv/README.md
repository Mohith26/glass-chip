# riscv: RVV planner kernels and a custom-instruction study

This folder is the RISC-V depth part of Glass Chip (stretch goals S1 and S2, study s13). I wrote
cuRobo-style motion-planner kernels and the T7 control step in scalar C and in RVV intrinsics, ran them
in gem5 to get CPI tables the SoC model can use, then defined one custom instruction (`xcol.sdf`, in an
extension I called Xglasscol) in my local copy of the RISC-V Unified Database, implemented it in gem5,
and pushed its measured speedup through the VX-1 model to see what it does to replan latency.

Two things to say up front:

- `xcol.sdf` is a design-space study. It sits in the custom-0 opcode space and is not a proposal for any
  vendor's ISA or for the standard. The interesting output is the method (formal definition, functional
  model, timing model, end-to-end effect), not the instruction.
- VX-1 is fictional. In the normal VX-1 mapping, TrajOpt's collision step runs on the SIMT cluster. The
  "collision on the app cores" configurations below are what-if mappings I built for this study.

All numbers below come from `riscv/tables/rvv_kernels.json` (written by `riscv/run_gem5.py`) and
`results/s13.json` (written by `studies/s13_riscv.py`).

## S1: RVV kernels

Setup: one RV64 core in gem5 26 SE mode with 64 KiB L1s, 1 MiB L2, 2 GHz, VLEN 256. MinorCPU is my
in-order proxy and O3CPU my app-core proxy. Each kernel call is one TrajOpt line-search evaluation for
4 seeds x 32 timesteps: 128 configurations, 7,808 sphere queries against an 80 x 80 x 50 ESDF, and
128 x 694 sphere pairs. Costs are marginal per call (difference between 2 and 4 calls).

| Kernel | CPU | Scalar cycles/call | RVV cycles/call | RVV speedup |
|---|---|---|---|---|
| Forward kinematics | Minor | 983,410 | 194,082 | 5.1x |
| Forward kinematics | O3 | 188,992 | 36,760 | 5.1x |
| ESDF collision | Minor | 1,510,098 | 299,106 | 5.0x |
| ESDF collision | O3 | 288,076 | 63,665 | 4.5x |
| Self-collision | Minor | 4,743,767 | 1,178,822 | 4.0x |
| Self-collision | O3 | 1,467,588 | 248,094 | 5.9x |
| T7 control step | Minor | 4,967 | 4,448 | 1.1x |
| T7 control step | O3 | 837 | 867 | 1.0x |

The T7 result is expected: the step is dominated by the serial Newton-Euler chain over 7 joints, and
only the per-joint Hermite, filter and impedance math vectorizes. VX-1's RT core has no vector unit
anyway, so the T7 RVV row is an app-core what-if.

Correctness: every variant on both CPU models dumps its outputs as raw bits, and all 27 verification
runs match the host reference (the same C sources compiled for the Mac) bit for bit. I build with
`-ffp-contract=off` so scalar, RVV, host and `xcol.sdf` all perform the same IEEE operations in the
same order; the self-collision RVV reduction reorders sums but still matched exactly on these inputs.
The scalar baselines are built with auto-vectorization off so they contain no vector code.

Caveat from the calibration work: gem5's RVV timing is coarse. Vector instructions are split into
per-register micro-ops on default functional units with no lane-width limit, so O3 RVV numbers are
optimistic.

The table the core reads is `tables/rvv_kernels.json`. It uses the same layout as
`calib/tables/cpu_gem5.json` (per kernel, per CPU model: cycles, instructions, CPI, cold cycles, runs
with gem5 command lines) plus a `cpu_cpi` section, per-item costs and the verification results.

## S2: Xglasscol and xcol.sdf in UDB

`xcol.sdf fd, xs1, xs2` is an R-type instruction in the custom-0 major opcode (`0b0001011`,
funct3 0, funct7 0, so `match: 0000000----------000-----0001011`). `xs1` points to a sphere record
`{cx, cy, cz, r}`, `xs2` to a 40-byte grid descriptor (origin, inverse voxel size, dimensions,
activation distance, base address). It writes `max(0, (r + eta) - trilinear(grid, c))` to `fd`,
NaN-boxed. The IDL in `operation()` spells out every step with the F extension's own softfloat helpers
(`f32_sub`, `f32_mul`, `f32_add`, `f32_to_ui32`, `ui32_to_f32`), round to nearest even, flags accrued,
no fused multiply-add, and memory reads through `read_memory` so translation and faults behave like
ordinary loads.

I added it as an overlay the way UDB's own custom extensions are organized: `spec/custom/isa/glasschip/`
with `ext/Xglasscol.yaml` and `inst/Xglasscol/xcol.sdf.yaml`, and `cfgs/glasschip_rv64.yaml`
(RV64GCV, VLEN 256, `arch_overlay: glasschip`).

Validation with UDB's own tooling (UDB commit 88cf3bf, Ruby 3.4.11 through UDB's `bin/mise`):

| Check | Command | Result |
|---|---|---|
| Config validity | `bin/udb validate cfg glasschip_rv64` | "Config glasschip_rv64 is valid" |
| Schema of every resolved arch file | `validate_overlay.rb` (Architecture#validate) | PASS |
| Encoding conflicts | `validate_overlay.rb` (same logic as `./do test:inst_encodings`) | PASS, against 1,378 RV64 instructions |
| IDL type check of the whole config | `validate_overlay.rb` (ConfiguredArchitecture#type_check, as `./do test:idl`) | PASS |
| Disassembly of the word my compiler emitted | `bin/udb disasm 0x00c5078b --config=glasschip_rv64` | `xcol.sdf` |
| Patch applies to a clean tree | `git apply --check riscv/udb/xglasscol.patch` on `git archive` of 88cf3bf | applies |

Why a script: `./do test:schema` and `./do test:inst_encodings` are hard-wired to the unconfigured
`_` architecture, which does not load custom overlays, and `udb validate spec --config=...` stopped
with a type error (the CLI passes a nil resolver), so `validate_overlay.rb` makes the same library
calls on the overlay config. Two local setup notes: UDB's prebuilt Z3 is a Linux shared object, so I
used the macOS arm64 `libz3.dylib` from the pip `z3-solver` 5.4.1 wheel (UDB pins 5.1.0), and I kept
all of UDB's tool state inside this project's `data/riscv/` folder.

To apply it to a UDB fork: `git apply riscv/udb/xglasscol.patch` from the UDB root.

## S2: xcol.sdf in gem5

gem5 is on a separate branch (`glasschip-xcol`, a worktree at `third_party/gem5-xcol`) built to
`build/RISCV_XCOL`, so the calibration build is untouched. The patch adds an `XcolSdf` op class, one
functional unit for it in the O3 and Minor pools, and the decoder entry. The execute code follows the
IDL line by line with gem5's softfloat, so it is bit-exact with the scalar C reference on all 7,808
queries for both CPU models and every latency setting.

What is timed and what is not:

- Timed: the instruction occupies its functional unit with a latency I set per run, and it flows
  through the pipeline like any other instruction.
- Not timed: its memory reads (4 sphere words, 9 descriptor fields, 8 corners) are done functionally, not through
  gem5's cache model. This is the main limitation of the study; see the bound below.
- Ordinary code is unaffected: the scalar ESDF run takes exactly the same cycles on the stock and the
  patched build (3,184,232 Minor, 653,098 O3 for 2 calls).

## Latency model

My assumption for one `xcol.sdf` unit: 4 cycles of address generation (subtract, multiply, clamp,
convert, index), a 2-cycle L1 hit plus 4 cycles for the 8 corner reads on 2 read ports, three levels
of linear interpolation at 4 cycles each (12), and 1 cycle for the hinge, rounded to 24 cycles of
latency with one new instruction every 4 cycles. MinorCPU can express that directly. O3CPU can only
model "pipelined every cycle" or "busy for the full latency", so for O3 I use latency 4, unpipelined
(one issue per 4 cycles) as the throughput proxy, and bracket it with latency 24 pipelined and <!-- numcheck: ignore (model inputs) -->
unpipelined. The software loop is unrolled 4x so independent instructions overlap.

| ESDF kernel | Minor cycles/query | O3 cycles/query |
|---|---|---|
| Scalar | 193.4 | 36.9 |
| RVV | 38.3 | 8.2 |
| xcol.sdf, headline model | 13.0 | 4.0 |

## End to end: T5 replan latency

`core_hook.py` builds T5 variants in which each of TrajOpt's five collision ops moves to the 8 RV64 app
cores as 8 shards (ESDF part, then self-collision part). Each shard's instruction count is its query
count times the measured instructions per query, and the core's CPU L2 hook turns that into cycles
with the measured O3 CPI (`set_l2_tables({"cpu_cpi": ...})`, CPU fidelity L2). Self-collision runs as
RVV in both the RVV and the xcol variants, so the instruction only speeds up part of the step.

What I take from it:

- On VX-1 as configured, the SIMT cluster is the right place for collision checking; moving it to the
  CPUs makes T5 four to five times slower even with RVV.
- If the CPUs have to do it (no SIMT, or SIMT busy), RVV is what makes it feasible, and `xcol.sdf`
  cuts the burst replan latency by about 23% (41.2 to 31.9 ms). <!-- src: results/s13.json#headline.s3_burst_xcol_vs_rvv_reduction_pct --> <!-- src: results/s13.json#headline.s3.rvv.t5_after_human_enter_mean_ms --> <!-- src: results/s13.json#headline.s3.xcol.t5_after_human_enter_mean_ms --> The bigger effect is on the rest of
  the system: shorter CPU occupancy during the burst reduced T6 state-estimation misses from 103 to
  20 across the three seeds.
- Self-collision is about half of the CPU collision cycles and the instruction does not touch it,
  which caps the end-to-end gain (Amdahl).
- The xcol numbers assume L1-hit corner reads. With the pessimistic memory bound above, the
  instruction would not beat RVV on O3.

## What did not work or is not done

- Apple clang has no RISC-V backend; everything RV64 is built with zig cc (LLVM 22, ld.lld, musl).
- gem5's RISC-V SE mode has no `readv` (syscall 65), which musl's `fread` uses, so the benchmark reads
  the ESDF file with `open`/`read`.
- In gem5 26 the O3 CPU takes its functional units from `instQueues[0].fuPool`, not `cpu.fuPool`. My
  first sweep set the wrong one and every O3 latency gave the same answer; the published table is from
  the corrected config.
- `xcol.sdf`'s memory reads are not timed through caches (see above).
- I did not build Spike; gem5 already had the RISC-V decoder and timing models I needed.
- The IK rollout op also does ESDF lookups, but it mixes them with kinematics in one op, so I left it on
  the SIMT cluster in every variant.
- The swept-sphere sub-samples are modeled as independent queries; I did not write a fused swept kernel.
